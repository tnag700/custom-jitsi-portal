# Графы для аудита кода

[Статья Positive Technologies](https://habr.com/ru/companies/pt/articles/1084780/)
предлагает соединить синтаксическое дерево (AST), пути выполнения (CFG) и
потоки данных (DFG), искать проверяемые пути и разбирать только релевантный
фрагмент. Для портала это две практические карты:

1. **Связи модулей backend.** Spring Modulith уже строит общую и отдельные
   диаграммы в `backend/build/spring-modulith-docs/`. На Windows: из `backend`
   выполнить `.\gradlew.bat architectureTest --tests '*BackendModulithDocumentationTest'`
   (в POSIX shell — `./gradlew` вместо `.\gradlew.bat`).
   `components.puml` показывает зависимости модулей, `module-*.puml` — связи
   выбранного модуля. ArchUnit дополнительно проверяет циклы и границы.
2. **Пути потока данных.** Новый workflow `.github/workflows/codeql.yml` строит
   базы CodeQL для Java и JavaScript/TypeScript на PR, при изменении `main`,
   еженедельно и вручную. Java анализирует реально скомпилированный backend;
   TypeScript анализируется без сборки. Набор `security-extended` ищет в том
   числе пути от входных данных до опасных операций. Находки и трассы доступны
   в GitHub → Security → Code scanning.

При аудите начните с затронутого модуля в `components.puml`, затем изучите
CodeQL alert и его путь от источника до стока, если он есть. Проверьте каждое
ребро пути по исходному коду и сопоставьте его с границами доверия из
[модели угроз](threat-model.md).
Для изменения без alert используйте диаграмму модуля, поиск вызовов и тесты;
отсутствие alert не доказывает безопасность.

CodeQL использует синтаксис, управление и поток данных для анализа, но здесь
нет единого сквозного графа через TypeScript, HTTP, Java, SQL, Keycloak и Jitsi.
Вызовы через DI, рефлексию и специфику Qwik нужно проверять вручную. Отчет
CodeQL пригоден для отбора и объяснения кандидатов, а не для утверждения, что
все пути проверены.
