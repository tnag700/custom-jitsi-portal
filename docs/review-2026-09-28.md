### Снятое замечание об аудите

Исходное утверждение «обычный async AFTER_COMMIT listener не имеет durable
publication» неверно. В `backend/build.gradle:24,43-45` уже подключён Spring
Modulith 2.1.0 с JDBC registry; миграция
`backend/src/main/resources/db/migration/V18__Create_event_publication_table.sql`
создаёт таблицу публикаций. События встреч публикуются из transactional use cases.
В [исходнике именно 2.1.0](https://github.com/spring-projects/spring-modulith/blob/2.1.0/spring-modulith-events/spring-modulith-events-core/src/main/java/org/springframework/modulith/events/support/PersistentApplicationEventMulticaster.java)
registry по умолчанию охватывает AFTER_COMMIT transactional listeners, включая
`MeetingAuditListener`; отдельная `@ApplicationModuleListener` не обязательна.
Ограничивающего `registry-trigger-annotation` в конфигурации проекта не найдено.

Сохранение публикации и восстановление её обработки — разные свойства.
В репозитории не найдено включение `republish-outstanding-events-on-restart`
или вызов повторной доставки meeting audit; pilot monitor/test относится к
config rollout. Это пробел доказательств восстановления, а не доказательство
утраты события. Task 8 теперь проверяет существующий registry, повторную
доставку и дубли. Новая durable-инфраструктура не требуется по этому ревью.
Runtime-проверка meeting audit с остановкой процесса пока не выполнена.

Приоритет измерений опирается на [четыре сигнала Google SRE](https://sre.google/sre-book/monitoring-distributed-systems/)
(задержка, трафик, ошибки, насыщение), а не на длину файла. Для SQL
использовать [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/18/using-explain.html);
для браузера — [LCP, INP, CLS и TTFB](https://web.dev/articles/vitals-tools);
для ёмкости Jitsi — [порядок ограничений JVB](https://jitsi.github.io/handbook/docs/devops-guide/devops-guide-requirements/)
(сначала сеть, затем RAM/CPU). [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/metrics/)
предупреждает о стоимости меток высокой кардинальности: tenant/user/meeting ID
не должны становиться метками Prometheus. [DORA](https://dora.dev/guides/dora-metrics/)
рекомендует оценивать доставку изменений по пяти метрикам и уменьшать размер
партий; это поддерживает независимые небольшие изменения вместо общего
переписывания приложения.
